#### 2. **关键方法重写**

##### (1) `calculateApportionRatio()` - 计算分摊比例

```java
@Override
public List<Map<String, BigDecimal>> calculateApportionRatio(
    Page<ReportAmazonBillDetailsEntity> feeList) {
    
    // 步骤1: 从上下文获取需要的分摊类型
    List<ApportionStrategyTypeEnum> apportionTypes = 
        CONTEXT_THREAD_LOCAL.get().list(APPORTION_TYPE_LIST, ApportionStrategyTypeEnum.class);
    
    // 步骤2: 根据分摊类型过滤出对应的适配器
    List<AbstractScToFbaApportionAdapter> adapters = 
        extractAdapters(scToFbaApportionAdapters, apportionTypes);
    
    // 步骤3: 每个适配器计算自己的分摊比例，然后合并
    List<Map<String, BigDecimal>> pctMapList = adapters.stream()
        .map(adapter -> adapter.calculateApportionRatio(feeList))
        .flatMap(List::stream)  // 将多个 List 展平成一个
        .toList();
    
    return pctMapList;
}
```

├── "2024-12-01-MSKU002" → 35.20
├── "2024-12-02-MSKU001" → 15.80
└── ...

### 四、关键逻辑深度剖析

#### 1. **分布式锁机制**

```java
// 构建锁key: finance:apportion:config_center:task_lock:Amazon:2024-12
String lockKey = String.format(TASK_LOCK_KEY, platform, yearMonth);

RLock lock = redissonClient.getLock(lockKey);

// 尝试获取锁，3秒超时
boolean isLocked = lock.tryLock(3, TimeUnit.SECONDS);

if (!isLocked) {
    throw new BizException(10001, "当前平台月份的费用分摊任务正在运行", null);
}

// 异步执行，完成后释放锁
CompletableFuture.runAsync(() -> {
    // 执行分摊任务
}).whenComplete((result, ex) -> {
    lock.forceUnlock();  // 无论成功失败都释放锁
});
```

**作用**: 防止同一平台同一月份的分摊任务并发执行，避免数据冲突。

#### 3. **分摊计算核心算法**

```java
// applyApportion 中的核心计算逻辑

for (int i = 0; i < pctMaps.size(); i++) {
    String fbaFieldName = fbaFieldNames.get(i);  // 目标字段
    Map<String, BigDecimal> pctMap = pctMaps.get(i);  // 分摊占比
    
    for (FinancePlatformProfitItemEntity fba : fbaList) {
        String dayMskuStr = fba.getMonthDay() + "-" + fba.getMsku();
        BigDecimal pct = pctMap.getOrDefault(dayMskuStr, BigDecimal.ZERO);
        
        // 从汇总费用实体获取总费用
        BigDecimal summaryFeeAmount = 
            (BigDecimal) PropertyUtils.getProperty(summaryFee, fbaFieldName);
        
        // 计算分摊金额 = 占比 * 总费用
        BigDecimal apportionAmount = NumberUtil.mul(pct, summaryFeeAmount)
            .divide(BigDecimal.valueOf(100), 8, RoundingMode.HALF_UP)
            .setScale(4, RoundingMode.HALF_UP);
        
        // 设置到 field_share 字段
        PropertyUtils.setProperty(fba, fbaFieldName + SHARE_SUFFIX, apportionAmount);
    }
}
```

**举例说明**:
```
汇总费用: sellingFees = 1000元

分摊占比:
- 2024-12-01-MSKU001: 30%
- 2024-12-01-MSKU002: 50%
- 2024-12-01-MSKU003: 20%

计算结果:
- MSKU001.sellingFee_share = 1000 * 0.30 = 300元
- MSKU002.sellingFee_share = 1000 * 0.50 = 500元
- MSKU003.sellingFee_share = 1000 * 0.20 = 200元
```

### 六、关键优势与设计亮点

#### 1. **高扩展性**
- 新增分摊类型只需实现一个新的 Adapter 子类
- 通过 `@ApportionTaskType` 注解自动注册
- 无需修改组合类代码

#### 2. **灵活组合**
- 可以动态配置需要执行的分摊类型
- 支持多种分摊策略的组合执行
- 通过 `extractAdapters` 过滤机制实现

#### 3. **异步处理**
- 使用 `CompletableFuture` 异步执行
- 不阻塞主线程
- 异常处理和日志记录完善

#### 4. **分布式安全**
- Redisson 分布式锁
- 防止并发执行
- 看门狗机制自动续期

#### 5. **完善的日志**
- 每个店铺站点独立日志
- 记录开始时间、结束时间、状态
- 异常信息保存

### 七、总结

`ScToFbaApportionComposite` 是一个**精心设计的组合适配器类**，它：

1. **统一管理**: 将多个分摊适配器组合在一起统一管理
2. **流程编排**: 定义了完整的分摊流程，确保各步骤有序执行
3. **动态选择**: 根据配置动态选择需要执行的分摊策略
4. **并发控制**: 通过分布式锁确保数据安全
5. **异常处理**: 完善的异常捕获和日志记录机制

这种设计使得系统能够灵活应对不同的分摊需求，同时保持代码的可维护性和可扩展性。
